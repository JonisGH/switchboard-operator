# Architecture and decisions

## Implemented in Milestone 1

This is a pnpm workspace with a Vite/React web app, a Fastify API and a small shared Zod health contract. The frontend requests `/api/health` through Vite's local proxy and validates the result. The backend endpoint is **liveness only**, not a database readiness or production health check. Docker Compose supplies PostgreSQL for local development; Prisma is configured but has **no models or migrations yet**. No request data is persisted.

TypeScript across frontend, backend, and contracts reduces boundary drift. Validation remains necessary at runtime: TypeScript alone does not validate HTTP payloads. A modular monolith is planned for Calls and WorkOrders because a small, evolving product needs domain boundaries but not separately deployed services. The first milestone only contains a single API route, not empty domain modules. The intended layers are React for the operator UI, Fastify for domain workflows, Prisma for data access, and PostgreSQL for persistence; the last two do not yet store domain data.

For the web UI, shadcn/ui primitives live in `apps/web/src/components/ui` and may use Tailwind internally. The foundation page composes Badge and Card, while its one-off layout lives beside it in `App.module.css`. `apps/web/src/index.css` is the single source of shared tokens: shadcn's semantic CSS colors and radius are mapped to Tailwind v4 utilities, and Tailwind-compatible typography, sizing, and spacing values serve both utilities and CSS Modules. Theme-independent values are separate from the light palette; setting `data-theme="dark"` on the document root overrides only the palette. Other named themes can follow the same override convention without changing components. The Tailwind `dark:` selector uses that same attribute, but there is no UI switcher, persistence, or automatic system-preference handling yet. Destructive styling is semantic; add success/warning tokens and variants when real statuses need them. Add application-specific components only when real workflows justify reusable semantics, rather than wrapping layout elements for their own sake.

## Intended domain workflow (not implemented)

An incoming **Call** records the interaction and its outcome. A **WorkOrder** represents actionable human follow-up and refers to its source Call. They are separate: a suitable request (such as opening hours) can end in a caller-confirmed `AI_RESOLVED` outcome with **no WorkOrder**, while `HUMAN_ACTION_REQUIRED` produces a WorkOrder. `TRANSFERRED` and `INCOMPLETE` remain explicit outcomes; neither is silently counted as AI resolved nor automatically given a WorkOrder without a documented rule. Initial cardinality is zero or one WorkOrder per Call, enforced when persistence is added, without assuming all Calls must have one. Multiple WorkOrders from a Call should only be introduced if later requirements justify it.

Technical processing status (queued, processing, completed, failed), Call outcome, and WorkOrder status are independent concepts. Call History includes *all* Calls; the Work Queue includes only WorkOrders requiring human action. AI resolution rate will use a documented denominator and count only caller-confirmed `AI_RESOLVED` outcomes in its numerator; `INCOMPLETE` is never counted as AI resolved.

When WorkOrders are introduced, default operational priority will be `NORMAL`; operators may later change it subject to future authorization rules. Ordering is explicit priority first, then oldest original arrival timestamp. Human review and source transcript comparison are planned before approval. A structured AI suggestion is not a human-approved summary.

## AI and processing boundaries (planned)

A future backend AI-provider interface will allow a deterministic mock first and another provider later. The provider will suggest structured request details, validated by the backend; it must not write arbitrary WorkOrders. Caller confirmation, not LLM self-assessment, determines the simulated `AI_RESOLVED` outcome. Mock processing may run synchronously initially. It is **not** a reliable background job system: production processing would need persisted jobs, timeouts, retries, idempotency, crash recovery, and progress reporting. Processing jobs are infrastructure work, separate from the Work Queue.

Real-time conversation and post-call processing have different needs. A future low-latency path could connect a telephony provider to streaming speech-to-text, LLM/dialog orchestration, and text-to-speech for the caller. Separately, a post-call path could process call audio into a higher-quality transcript and structured summary before the backend records the Call outcome and conditionally creates a WorkOrder. A future transcription service might be extracted into Python using KB-Whisper if quality, performance, or operational needs justify it. None of these integrations, services, or paths is implemented yet.

PostgreSQL is the initial source for operational data. Calls, WorkOrders, processing state, idempotency records, and events/audit records could eventually live there if requirements justify each. It does not replace every specialized system indefinitely: **add infrastructure when a demonstrated requirement justifies it**, rather than introducing queues, caches, or search services in advance.

## Security and operational limitations

Only fictional information belongs in this prototype. Local DB credentials are demonstration-only. There is no authentication, authorization, audit trail, encrypted recording storage, data retention policy, or applicable privacy/regulatory assessment. Do not expose this app to real caller traffic. The API does not log transcripts because there are no transcripts yet; future routes must avoid logging sensitive request bodies. Do not commit secrets.
