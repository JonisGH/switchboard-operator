# Architecture and decisions

## Implemented through Milestone 3

This is a pnpm workspace with a Vite/React web app, a Fastify API and shared Zod HTTP contracts. The frontend requests `GET /calls` and `GET /work-orders` through Vite's local proxy and validates both responses. `GET /health` remains **liveness only**, not a database readiness or production health check. Docker Compose supplies PostgreSQL for local development; Prisma reads and writes persisted Call and WorkOrder records through the PostgreSQL driver adapter. Fictional, idempotent seeds cover all four Call outcomes, an undetermined outcome, and one eligible WorkOrder.

TypeScript across frontend, backend, and contracts reduces boundary drift. Validation remains necessary at runtime: TypeScript alone does not validate HTTP payloads. A modular monolith gives Calls and WorkOrders boundaries without separately deployed services. The implemented layers are React for the operator UI, Fastify for business endpoints, Prisma for data access, and PostgreSQL for persistence. Call History orders by `Call.startedAt` descending and Call ID descending; the active Work Queue orders by originating `Call.startedAt` ascending and `callId` ascending as a stable tie-breaker. The latter preserves original caller waiting time even when the WorkOrder is created later.

The Call model has a UUID ID; nullable caller reference, category, and outcome; required `startedAt` and database-defaulted `createdAt`; and nullable `endedAt`. `startedAt` must be supplied as the real-world call start, while `createdAt` records when the row was persisted. An undetermined outcome is `null`, not `INCOMPLETE`. Outcome is a PostgreSQL enum; category remains a nullable string because request taxonomies can evolve. A WorkOrder has a required unique `callId` foreign key, title, nullable description, status (`OPEN`, `IN_PROGRESS`, `RESOLVED`; default `OPEN`), and database-defaulted `createdAt`. Unique `callId` enforces zero or one WorkOrder per Call; deleting a Call with a WorkOrder is restricted. The migration SQL contains PostgreSQL CHECK constraints for Call chronology and a non-whitespace WorkOrder title; Prisma Schema Language cannot represent them, so retain them in migration history. No priority, assignee, or AI summary fields exist.

For the web UI, shadcn/ui primitives live in `apps/web/src/components/ui` and may use Tailwind internally. Call History and the Work Queue compose Table, Badge, Card, and Button; their styles are colocated in CSS Modules. `apps/web/src/index.css` is the single source of shared tokens: shadcn's semantic CSS colors and radius are mapped to Tailwind v4 utilities, and Tailwind-compatible typography, sizing, and spacing values serve both utilities and CSS Modules. Theme-independent values are separate from the light palette; setting `data-theme="dark"` on the document root overrides only the palette. Other named themes can follow the same override convention without changing components. The Tailwind `dark:` selector uses that same attribute, but there is no UI switcher, persistence, or automatic system-preference handling yet. Status badges use semantic tokens with text labels, not color alone. Add application-specific components only when real workflows justify reusable semantics, rather than wrapping layout elements for their own sake.

WorkOrder creation is available through `POST /calls/:callId/work-order` for an already recorded `HUMAN_ACTION_REQUIRED` Call. The backend validates input, checks eligibility, and returns an existing WorkOrder on retry. A unique database constraint on `callId` prevents duplicates under concurrent creation; a unique-conflict retry reads and returns the winner. `AI_RESOLVED`, `TRANSFERRED`, `INCOMPLETE`, and undetermined Calls cannot create WorkOrders through this endpoint. PostgreSQL enforces the relationship and uniqueness, but the cross-table eligibility rule lives in the backend. The active `GET /work-orders` includes `OPEN` and `IN_PROGRESS`, not `RESOLVED`. There is no general Call creation or outcome-update endpoint yet.

## Planned next: simulated call workflow and human review

An incoming **Call** records the interaction and its outcome. A **WorkOrder** represents actionable human follow-up. A future simulated conversation will demonstrate caller-confirmed `AI_RESOLVED` without a WorkOrder and `HUMAN_ACTION_REQUIRED` with one; stored seed outcomes do not simulate this process. `TRANSFERRED` and `INCOMPLETE` remain explicit outcomes with no automatic WorkOrder rule. Recording an outcome and conditionally creating its WorkOrder should happen in one database transaction. Multiple WorkOrders per Call should be considered only if actual requirements justify changing the unique `callId` constraint.

Technical processing status (queued, processing, completed, failed), Call outcome, and WorkOrder status are independent concepts. Call History includes *all* Calls; the Work Queue includes only actionable WorkOrders. AI resolution rate will use a documented denominator and count only caller-confirmed `AI_RESOLVED` outcomes in its numerator; `INCOMPLETE` is never counted as AI resolved. Neither AI resolution metrics nor outcome determination from a real conversation are implemented yet.

There is no operational priority field or editing control yet. If operators need prioritization, add it with explicit assignment rules and history instead of giving every WorkOrder a decorative default. Human review and source transcript comparison are planned before approval. A structured AI suggestion is not a human-approved summary.

## Future architecture considerations (not implemented)

A future backend AI-provider interface will allow a deterministic mock first and another provider later. The provider will suggest structured request details, validated by the backend; it must not write arbitrary WorkOrders. Caller confirmation, not LLM self-assessment, determines the simulated `AI_RESOLVED` outcome. Mock processing may run synchronously initially. It is **not** a reliable background job system: production processing would need persisted jobs, timeouts, retries, idempotency, crash recovery, and progress reporting. Processing jobs are infrastructure work, separate from the Work Queue.

Real-time conversation and post-call processing have different needs. A future low-latency path could connect a telephony provider → dedicated realtime call runtime → streaming speech-to-text / LLM dialog orchestration / text-to-speech → caller. **BEAM/Elixir is an option to evaluate for that runtime**, not a selection or requirement: lightweight processes, supervision trees, fault isolation, message passing, and telecom heritage could be useful for many concurrent calls. Compare those advantages with Node.js or provider-hosted orchestration, team expertise, integration cost, operational complexity, measured latency, and recovery requirements before choosing. The existing Fastify service would remain the business API and persistence boundary for Calls and WorkOrders; a separate runtime would submit validated, idempotent state changes through it rather than own business records. No realtime service or new runtime dependency exists today.

Separately, a post-call path could process call audio into a higher-quality transcript and structured summary before the backend records the Call outcome and conditionally creates a WorkOrder. A future transcription service might be extracted into Python using KB-Whisper if quality, performance, or operational needs justify it. None of these integrations, services, or paths is implemented yet.

PostgreSQL is the initial source for operational data. Calls, WorkOrders, processing state, idempotency records, and events/audit records could eventually live there if requirements justify each. It does not replace every specialized system indefinitely: **add infrastructure when a demonstrated requirement justifies it**, rather than introducing queues, caches, or search services in advance.

## Security and operational limitations

Only fictional information belongs in this prototype. Local DB credentials are demonstration-only. There is no authentication, authorization, audit trail, encrypted recording storage, data retention policy, or applicable privacy/regulatory assessment. `POST /calls/:callId/work-order` is unauthenticated: do not expose this app to real caller traffic. The API does not log transcripts because there are no transcripts yet; future routes must avoid logging sensitive request bodies. Do not commit secrets.
