# Architecture and decisions

## Implemented through Milestone 4

This is a pnpm workspace with a Vite/React web app, a Fastify API and shared Zod HTTP contracts. The frontend requests `GET /calls` and `GET /work-orders` through Vite's local proxy and validates both responses. `POST /simulated-calls` runs one of four fictional backend scenarios and returns the persisted Call result plus an optional WorkOrder. `GET /health` remains **liveness only**, not a database readiness or production health check. Docker Compose supplies PostgreSQL; Prisma persists Calls, WorkOrders, fictional text transcripts and structured suggestions. Seeds remain idempotent and distinct from simulated processing.

TypeScript across frontend, backend, and contracts reduces boundary drift. Validation remains necessary at runtime: TypeScript alone does not validate HTTP payloads. A modular monolith gives Calls and WorkOrders boundaries without separately deployed services. The implemented layers are React for the operator UI, Fastify for business endpoints, Prisma for data access, and PostgreSQL for persistence. Call History orders by `Call.startedAt` descending and Call ID descending; the active Work Queue orders by originating `Call.startedAt` ascending and `callId` ascending as a stable tie-breaker. The latter preserves original caller waiting time even when the WorkOrder is created later.

The Call model has a UUID ID; nullable caller reference, category, and outcome; required `startedAt` and database-defaulted `createdAt`; and nullable `endedAt`. `startedAt` is the real-world call start, while `createdAt` records when the row was persisted. An undetermined outcome is `null`, not `INCOMPLETE`. A simulated Call also records a nullable, backend-validated `simulationScenarioKey`, fictional `transcript`, and `aiSuggestion` JSONB artifact. The suggestion is validated at write/read boundaries with `schemaVersion: 1`, a suggested title/category, summary, caller request, and clarification questions. It is not human-approved content. A WorkOrder has a required unique `callId` foreign key, title, nullable description, status (`OPEN`, `IN_PROGRESS`, `RESOLVED`; default `OPEN`), and database-defaulted `createdAt`. Unique `callId` enforces zero or one WorkOrder per Call; deleting a Call with a WorkOrder is restricted. Migration SQL contains PostgreSQL CHECK constraints for Call chronology and a non-whitespace WorkOrder title, which Prisma Schema Language cannot represent. No priority or assignee fields exist.

For the web UI, shadcn/ui primitives live in `apps/web/src/components/ui` and may use Tailwind internally. Call History and the Work Queue compose Table, Badge, Card, and Button; their styles are colocated in CSS Modules. `apps/web/src/index.css` is the single source of shared tokens: shadcn's semantic CSS colors and radius are mapped to Tailwind v4 utilities, and Tailwind-compatible typography, sizing, and spacing values serve both utilities and CSS Modules. Theme-independent values are separate from the light palette; setting `data-theme="dark"` on the document root overrides only the palette. Other named themes can follow the same override convention without changing components. The Tailwind `dark:` selector uses that same attribute, but there is no UI switcher, persistence, or automatic system-preference handling yet. Status badges use semantic tokens with text labels, not color alone. Add application-specific components only when real workflows justify reusable semantics, rather than wrapping layout elements for their own sake.

WorkOrder creation is available through `POST /calls/:callId/work-order` for an already recorded `HUMAN_ACTION_REQUIRED` Call. The backend validates input, checks eligibility, and returns an existing WorkOrder on retry. A unique database constraint on `callId` prevents duplicates under concurrent creation; a unique-conflict retry reads and returns the winner. `AI_RESOLVED`, `TRANSFERRED`, `INCOMPLETE`, and undetermined Calls cannot create WorkOrders through this endpoint. PostgreSQL enforces the relationship and uniqueness, but the cross-table eligibility rule lives in the backend. The active `GET /work-orders` includes `OPEN` and `IN_PROGRESS`, not `RESOLVED`. There is no general non-simulation Call creation or outcome-update endpoint yet.

The simulated workflow creates a pending Call with its versioned fixture key and fictional transcript. A backend mock provider suggests structured content; a separate fictional caller response determines the outcome. A conditional `UPDATE ... WHERE outcome IS NULL` plus eligibility-checked WorkOrder insertion runs inside one Prisma transaction. A failed WorkOrder insert rolls back the terminal outcome and suggestion, leaving the pending Call retryable. The existing WorkOrder rule is shared between this transaction and the standalone creation endpoint; unique-conflict recovery for standalone requests happens outside aborted transactions. Matching completed simulation retries return persisted content unchanged, a different scenario key (or an unrelated Call ID) returns 409, and concurrent requests cannot create a second WorkOrder. The client-generated Call UUID is a demo-specific retry identity, not a telephony idempotency strategy. No technical processing-status fields were added.

## Planned next: human review

An incoming **Call** records the interaction and its outcome. A **WorkOrder** represents actionable human follow-up. The mock workflow now demonstrates caller-confirmed `AI_RESOLVED` without a WorkOrder and `HUMAN_ACTION_REQUIRED` with one. `TRANSFERRED` and `INCOMPLETE` remain explicit outcomes with no automatic WorkOrder rule. A future review view should compare the persisted fictional transcript with the AI suggestion and allow human edits without overwriting them on retry. Multiple WorkOrders per Call should be considered only if actual requirements justify changing the unique `callId` constraint.

For the planned simulation, a client-generated Call ID is a demo-specific retry identity, **not** the general idempotency strategy for future telephony integrations. The nullable `simulationScenarioKey` records a backend-defined versioned fixture key; a retry must compare this stored key directly, not infer the scenario from the transcript or suggestion. Only fictional text transcripts belong in this milestone. A production implementation would need an explicit retention, privacy, and storage design for transcripts and call audio before handling real callers.

Call outcome and WorkOrder status are persisted **business state**. The mock process runs synchronously; no durable processing jobs exist yet. Call History includes *all* Calls; the Work Queue includes only actionable WorkOrders. AI resolution rate, if later shown, needs a documented denominator and counts only caller-confirmed `AI_RESOLVED` outcomes in its numerator; `INCOMPLETE` is never counted as AI resolved. A fictional confirmed outcome is not proof of real-world resolution.

There is no operational priority field or editing control yet. If operators need prioritization, add it with explicit assignment rules and history instead of giving every WorkOrder a decorative default. Human review and source transcript comparison are planned before approval. A structured AI suggestion is not a human-approved summary.

## Future architecture considerations (not implemented)

A replaceable backend AI-provider interface currently has one deterministic mock. The provider suggests structured request details, validated by the backend; it does not write WorkOrders or decide whether a caller was satisfied. Synchronous mock processing is **not** a reliable background job system. Future transcription → summarization → classification pipelines should be modeled as durable jobs/outbox records, not many mutable technical-status fields on Call or WorkOrder. Evaluate PostgreSQL-first claiming/leases, retries, timeouts, idempotency, recovery and transactional outbox delivery before adding a broker. PostgreSQL `LISTEN/NOTIFY` could wake workers, but is **not** a durable queue: workers must recover missed notifications by querying persisted work. Add external queue infrastructure only when demonstrated scale or reliability requirements justify it.

Real-time conversation and post-call processing have different needs. A future low-latency path could connect a telephony provider → dedicated realtime call runtime → streaming speech-to-text / LLM dialog orchestration / text-to-speech → caller. **BEAM/Elixir is an option to evaluate for that runtime**, not a selection or requirement: lightweight processes, supervision trees, fault isolation, message passing, and telecom heritage could be useful for many concurrent calls. Compare those advantages with Node.js or provider-hosted orchestration, team expertise, integration cost, operational complexity, measured latency, and recovery requirements before choosing. The existing Fastify service would remain the business API and persistence boundary for Calls and WorkOrders; a separate runtime would submit validated, idempotent state changes through it rather than own business records. No realtime service or new runtime dependency exists today.

Separately, a post-call path could process call audio into a higher-quality transcript and structured summary before the backend records the Call outcome and conditionally creates a WorkOrder. A future transcription service might be extracted into Python using KB-Whisper if quality, performance, or operational needs justify it. None of these integrations, services, or paths is implemented yet.

The current shared Zod contracts cover a small monorepo. Evaluate backend-owned OpenAPI/Swagger as the API grows, potentially generating a TypeScript frontend client rather than increasing direct frontend/backend code sharing. No OpenAPI generator or client is implemented. A real AI architecture evaluation must compare streaming STT, LLM/dialog orchestration, TTS, higher-quality post-call transcription, provider choices, accuracy, latency, cost, data retention, GDPR/privacy requirements, and geographic processing/storage constraints before selecting integrations.

PostgreSQL is the initial source for operational data. Calls, WorkOrders, processing state, idempotency records, and events/audit records could eventually live there if requirements justify each. It does not replace every specialized system indefinitely: **add infrastructure when a demonstrated requirement justifies it**, rather than introducing queues, caches, or search services in advance.

## Security and operational limitations

Only fictional information belongs in this prototype, including the persisted text transcripts. A production system would require an explicit retention, privacy, and storage design for transcripts and call audio before accepting real callers. Local DB credentials are demonstration-only. There is no authentication, authorization, audit trail, encrypted recording storage, retention policy, or applicable privacy/regulatory assessment. Both POST endpoints are unauthenticated: do not expose this app to real caller traffic. Fastify request logging must not include transcripts or suggestion payloads. Do not commit secrets.
